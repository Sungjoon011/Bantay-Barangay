System Architecture & Q&A Defense Blueprint

Comprehensive breakdown of backend engineering, database normalization, security, and trigger mechanics for live instructor evaluation.

3rd Normal Form (3NF) Compliance

All entities strictly eliminate transitive functional dependencies. Separate models exist for roles, users, residents, incidents, and certificate_requests with zero redundant text duplicates.

Junction Tables Implemented:
  • user_roles (Composite PK: userId + roleId)
  • incident_responders (Composite PK: incidentId + residentId)
Triggers & Stored Procedures

Business calculations and transaction logs do not run in Node.js application memory. They run natively in the PostgreSQL database engine.

Trigger: trigger_incident_audit (AFTER UPDATE/DELETE)
Stored Proc: update_incident_status(id, status, updated_by)
Security & SQL Injection Neutralization

Raw SQL string concatenations are strictly forbidden. Data payloads route into PostgreSQL via Prisma Prepared Statements. The app connects using restricted database role app_user instead of root superuser permissions.

Cloud Relational Hosting

Production environment configured with zero reliance on local database instances. Connected live to managed serverless PostgreSQL instance (Neon / Supabase) with SSL connection string routing.

Instructor "What-If" Defense Preparedness

Q: "What happens if I manually delete a parent user row directly in the database GUI?"

A: Explicit referential cascade constraints (onDelete: Cascade) will delete associated resident profiles, preventing orphaned foreign key rows in production.

Q: "How do you verify audit logs aren't faked by frontend JS?"

A: Audit logs are recorded directly by the PostgreSQL database engine trigger process_incident_audit_log() during the database transaction cycle, bypassing application logic.
